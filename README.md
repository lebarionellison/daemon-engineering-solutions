## Stripe payment verification (live checkout remains disabled)

### Worker configuration

In Cloudflare Dashboard, open **Workers & Pages → daemon-engineering-solutions → Settings → Variables and Secrets** and add the following as an encrypted secret:

- `STRIPE_WEBHOOK_SECRET` — the signing secret generated by the Stripe webhook endpoint.

Do not place the secret in GitHub source, browser JavaScript, a public environment variable, or a chat message.

The Worker expects Stripe events at:

`https://daemon-engineering-solutions.lebarionellison.workers.dev/api/stripe/webhook`

Configure the Stripe webhook endpoint to send only:

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`

The endpoint verifies the Stripe-Signature HMAC against the raw request body, rejects stale signatures, accepts only paid USD Checkout Sessions matching the two catalog product codes and exact amounts, and records the event/session in D1 with unique constraints for idempotency.

## Customer preflight and paid configuration workflow (merged into main)

The main branch includes:
- A visitor-supplied engineering goal and Kubernetes YAML submission to `POST /api/preflight`.
- Server-side heuristic findings and an optional AI-generated proposed configuration using the encrypted `OPENAI_API_KEY` Worker secret.
- A free preview that withholds the complete generated file.
- A server-created Stripe Checkout Session for the $9 Hardened Configuration price selected by `ACE_HARDENED_PRICE_ID`, with the receipt ID attached as Checkout Session metadata.
- A purchase claim endpoint that returns the configuration only after the signed Stripe webhook records a paid session linked to that receipt. The claim is single-use.

### Additional deployment requirements

Add these as **encrypted Worker secrets** (never browser variables):
- `OPENAI_API_KEY`
- `STRIPE_SECRET_KEY` (use a test-mode key for sandbox testing; only switch to a live key for an intentional production launch)
- `STRIPE_WEBHOOK_SECRET` (must come from a webhook destination in the same Stripe mode)

Add `ACE_HARDENED_PRICE_ID` as a non-secret Worker environment variable containing the `$9` Price ID from the same Stripe mode as `STRIPE_SECRET_KEY`. Test and live Price IDs are different. The webhook rejects events whose `livemode` flag does not match the configured key mode.

The existing `DB` D1 binding must be present. Apply migrations in order, including:
- `migrations/0003_create_purchases.sql`
- `migrations/0004_link_purchases_to_receipts.sql`

The existing Stripe webhook must remain configured for `checkout.session.completed` and `checkout.session.async_payment_succeeded`. The $9 checkout endpoint creates a new Checkout Session directly; it does not use the old deactivated Payment Link.

### Important current boundaries

- The AI output is a proposal, not a validated or production-ready configuration. The Gatekeeper remains limited text-pattern screening; no YAML parser, Kubernetes dry-run, Terraform plan, tests, vulnerability scan, or live cluster connection is added by this change.
- The purchase claim uses the unguessable Stripe Checkout Session ID and an atomic single-use D1 fulfillment state. The success page retries briefly while the Stripe webhook records payment. Customer email delivery and a customer account/download library are not implemented.
- GitHub PR creation is **not enabled**. A secure customer-owned GitHub integration requires a GitHub App/OAuth authorization flow with per-customer repository grants, installation-token handling, webhook/state validation, and explicit repository/file consent. A shared owner PAT is not an acceptable substitute.
- Production deployment and payment fulfillment still require the documented D1 migrations, secrets, webhook configuration, and end-to-end verification. Do not test with a real charge.


## ROS 2 Evolution Engineering

DAEMON ACE is being developed as a release-aware engineering layer above upstream ROS 2. It does not fork or replace ROS 2 and does not control upstream release dates.

### Upstream lifecycle targets (checked 2026-11-17)

| Distribution | Upstream status | Release / support window | DAEMON ACE validation position |
|---|---|---|---|
| Lyrical Luth | Current LTS | Released 2026-05-22; upstream EOL May 2031 | Primary forward baseline; compatibility claim requires passing CI matrix |
| Makoa Mata-mata | Planned non-LTS | Planned May 2027; planned EOL December 2028 | Pre-release target once upstream packages are available; not released |
| Rolling Ridley | Continuous development | Rolling development channel | Early-warning lane; not a production stability guarantee |
| Jazzy Jalisco | Supported LTS | Released May 2024; upstream EOL May 2029 | Customer legacy baseline; validate per CI result |
| Humble Hawksbill | Supported LTS | Released May 2022; upstream EOL May 2027 | Existing verified talker/listener smoke-test baseline |

Upstream schedule and status:
- https://github.com/ros2/ros2_documentation/blob/rolling/source/Releases.rst
- https://github.com/ros2/ros2/releases
- https://docs.ros.org/en/rolling/Releases/Release-Makoa-Mata-mata.html

### DAEMON ACE validation levels

1. **Build/package:** dependency resolution and workspace compilation.
2. **Messaging:** ROS 2 publisher/subscriber talker-listener smoke tests.
3. **Interface and QoS:** planned package/API/message compatibility and DDS/QoS scenario checks.
4. **Simulation:** planned simulator regression (e.g. Gazebo / Isaac Sim) with versioned test scenarios.
5. **Hardware qualification:** separately authorized testing on named physical platforms with documented lab procedures.

The GitHub Actions workflow `.github/workflows/daemon-preflight.yml` runs the matrix on relevant pull requests and pushes to main. The standalone `.github/workflows/ros2-evolution.yml` workflow repeats it weekly and supports manual dispatch. Both test Humble, Jazzy, Lyrical and Rolling. A passing messaging job proves only that the tested ROS 2 demo publisher and subscriber exchanged messages in that CI container. It does not prove complete distribution compatibility, simulator fidelity, physical robot behavior, real-time performance, functional safety or production readiness. Makoa is not included in the runnable matrix until upstream prerelease packages are available.

**Release discipline:** never mark a ROS distribution as DAEMON ACE supported from its upstream release announcement alone. Publish the exact CI run, tested image/distro, test scope and limitations with each compatibility update.
