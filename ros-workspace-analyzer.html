01 / ANALYSIS PIPELINE

FROM CUSTOMER WORKSPACE TO MIGRATION EVIDENCE.

One repeatable workflow separates static review signals from actual per-distribution build outcomes.

01 · DISCOVER

Package + dependency graph

Read package.xml manifests, enumerate package versions and declared dependencies, and flag external rosdep keys for target-specific resolution.

02 · COMPARE

API migration signals

Apply a versioned, inspectable migration rule set to identify common ROS 1 remnants and known API patterns requiring engineering review.

03 · INSPECT

DDS + QoS configuration

Surface reliability, durability, history/depth and system-default patterns with recommendations for explicit policy review.

04 · BUILD

Distribution matrix

Optionally run rosdep resolution and colcon builds inside official ROS containers for each selected target distribution.

05 · REPORT

Versioned compatibility receipt

Generate JSON and Markdown outputs with analyzer version, workspace SHA-256, targets, findings, build status and limitations.

06 · REVIEW

Engineer-led disposition

Prioritize action-required findings, review recommendations and unresolved dependencies before approving a migration plan.

02 / EXECUTION

STATIC FIRST. BUILD WHEN YOU'RE READY.

The analyzer is local-first. Static inspection does not need Docker. Actual multi-distro builds are explicitly opt-in and require Docker plus network access.

STATIC REVIEW · LOCAL PYTHON
python3 ros2/workspace_analyzer/analyze.py ./my_ros_ws --distro humble --distro jazzy --distro lyrical

# Actual rosdep + colcon builds in ROS containers
python3 ros2/workspace_analyzer/analyze.py ./my_ros_ws \
  --build --distro humble --distro jazzy \
  --distro lyrical --distro rolling

# Output artifacts
daemon-ace-report/
  ros-workspace-compatibility-report.json
  ros-workspace-compatibility-report.md
Build matrix runs only with --build. A distro is marked passed only when its containerized dependency resolution and colcon build exit successfully. Static-only targets are reported as not-run—not passed.

04 / REPORT CONTRACT

EVERY RESULT HAS A TRACEABLE CONTEXT.

The report schema is daemon-ace.ros2-workspace-report.v1. It records the analyzer and report version, workspace fingerprint, package inventory, target matrix, findings, summary and limitations.

REPORT SHAPE · JSON
{
  "schema": "daemon-ace.ros2-workspace-report.v1",
  "report_version": "1.0.0",
  "workspace": {
    "sha256": "<content fingerprint>",
    "packages": ["<discovered package inventory>"]
  },
  "targets": ["humble", "jazzy", "lyrical"],
  "build_matrix": [
    {"distro": "humble", "status": "passed | failed | not-run"}
  ],
  "findings": [
    {"severity": "high | medium | info", "code": "<rule-id>"}
  ],
  "summary": {"disposition": "<review status>"}
}
05 / MIGRATION DIFF + QOS CONTRACT

SEE THE DELTA. VALIDATE THE POLICY.

Version 1.1.0 compares a candidate workspace against a baseline and validates a structured DAEMON ACE QoS profile before a migration review.

WORKSPACE DIFF

Package + dependency changes

Detect package additions/removals, manifest dependency changes, package version changes and CMake find_package additions/removals.

API USAGE DELTA

Recognized source patterns

Compare versioned API migration rule occurrence counts and candidate source locations between the before and after workspace.

QOS PROFILE CONTRACT

Publisher / subscriber checks

Validate required policy fields, enums, history depth, timing values and selected reliability/durability request-offered compatibility.

BASELINE + CANDIDATE REVIEW
python3 ros2/workspace_analyzer/analyze.py ./candidate_ws \\\n  --compare-to ./baseline_ws \\\n  --qos-profile ros2/workspace_analyzer/examples/qos-profile.example.json \\\n  --distro humble --distro jazzy --distro lyrical --distro rolling
This is a source/workspace delta, not an upstream ROS SDK header or binary ABI diff. QoS validation checks the DAEMON ACE JSON contract and selected request/offered policies; it does not parse arbitrary ROS parameter YAML or test a live DDS graph.
06 / VALIDATION BOUNDARY

BUILD PASS IS NOT ROBOT QUALIFICATION.

Static API rules are heuristic and may produce false positives or miss indirect usage. DDS/QoS source inspection is not a live middleware interoperability test. A successful colcon build does not prove application correctness, runtime behavior under load, simulator fidelity, physical hardware readiness, real-time performance or safety certification. Those require separately scoped tests, environments and authorization.
