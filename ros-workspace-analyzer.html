01 / ANALYSIS PIPELINE

FROM CUSTOMER WORKSPACE TO MIGRATION EVIDENCE.

One repeatable workflow separates static review signals from actual per-distribution build outcomes.

01 · DISCOVER

Package + dependency graph

Read package.xml manifests, enumerate package versions and declared dependencies, and flag external rosdep keys for target-specific resolution.

02 · COMPARE

API migration signals

Apply a versioned, inspectable migration rule set to identify common ROS 1 remnants and known API patterns requiring engineering review.

03 · INSPECT

DDS + QoS configuration

Surface reliability, durability, history/depth and system-default patterns with recommendations for explicit policy review.

04 · BUILD

Distribution matrix

Optionally run rosdep resolution and colcon builds inside official ROS containers for each selected target distribution.

05 · REPORT

Versioned compatibility receipt

Generate JSON and Markdown outputs with analyzer version, workspace SHA-256, targets, findings, build status and limitations.

06 · REVIEW

Engineer-led disposition

Prioritize action-required findings, review recommendations and unresolved dependencies before approving a migration plan.

02 / EXECUTION

STATIC FIRST. BUILD WHEN YOU'RE READY.

The analyzer is local-first. Static inspection does not need Docker. Actual multi-distro builds are explicitly opt-in and require Docker plus network access.

STATIC REVIEW · LOCAL PYTHON
python3 ros2/workspace_analyzer/analyze.py ./my_ros_ws --distro humble --distro jazzy --distro lyrical

# Actual rosdep + colcon builds in ROS containers
python3 ros2/workspace_analyzer/analyze.py ./my_ros_ws \
  --build --distro humble --distro jazzy \
  --distro lyrical --distro rolling

# Output artifacts
daemon-ace-report/
  ros-workspace-compatibility-report.json
  ros-workspace-compatibility-report.md
Build matrix runs only with --build. A distro is marked passed only when its containerized dependency resolution and colcon build exit successfully. Static-only targets are reported as not-run—not passed.

04 / REPORT CONTRACT

EVERY RESULT HAS A TRACEABLE CONTEXT.

The report schema is daemon-ace.ros2-workspace-report.v2 and report version is 1.1.0. It records analyzer/rule versions, workspace fingerprint and inventory, target/build matrix, findings, optional baseline diff, optional structured QoS validation, optional cross-distribution catalog comparison, summary and explicit limitations.

REPORT SHAPE · JSON
{
  "schema": "daemon-ace.ros2-workspace-report.v2",
  "report_version": "1.1.0",
  "workspace": {
    "sha256": "<content fingerprint>",
    "packages": ["<discovered package inventory>"]
  },
  "targets": ["humble", "jazzy", "lyrical"],
  "build_matrix": [
    {"distro": "humble", "status": "passed | failed | not-run"}
  ],
  "findings": [
    {"severity": "high | medium | info", "code": "<rule-id>"}
  ],
  "summary": {"disposition": "<review status>"}
}
05 / MIGRATION DIFF + QOS CONTRACT

SEE THE DELTA. VALIDATE THE POLICY.

Version 1.1.0 compares a candidate workspace against a baseline and validates a structured DAEMON ACE QoS profile before a migration review.

WORKSPACE DIFF

Package + dependency changes

Detect package additions/removals, manifest dependency changes, package version changes and CMake find_package additions/removals.

API USAGE DELTA

Recognized source patterns

Compare versioned API migration rule occurrence counts and candidate source locations between the before and after workspace.

QOS PROFILE CONTRACT

Publisher / subscriber checks

Validate required policy fields, enums, history depth, timing values and selected reliability/durability request-offered compatibility.

CROSS-DISTRO CATALOG

Installed API + package deltas

Inventory ROS packages, versions, public headers and declaration tokens in each selected distro container, then compare adjacent distributions for package, header and API-token changes.

BASELINE + CANDIDATE REVIEW
python3 ros2/workspace_analyzer/analyze.py ./candidate_ws \\\n  --compare-to ./baseline_ws \\\n  --qos-profile ros2/workspace_analyzer/examples/qos-profile.example.json \\\n  --build --distro humble --distro jazzy --distro lyrical --distro rolling
Workspace deltas compare customer baseline to candidate. The container catalog separately compares installed ROS package versions, public headers and regex-extracted declaration tokens across selected distributions; it is not an AST, semantic API or binary ABI diff. QoS validation checks the DAEMON ACE JSON contract and selected request/offered policies, not arbitrary ROS parameter YAML or a live DDS graph.
06 / PLATFORM ROADMAP

THE ANALYZER IS THE FIRST GATE IN A LARGER ROBOTICS PIPELINE.

DAEMON ACE is being developed as an engineering layer above ROS 2. The current analyzer provides workspace and migration evidence; additional stages are explicitly roadmap or research work.

AVAILABLE FOUNDATION

Workspace intelligence

Analyzer v1.1.0: baseline diffs, package/dependency review, QoS JSON contract checks, optional ROS container builds and versioned schema-v2 reports.

IN DEVELOPMENT

Communication assurance

Expand existing CI messaging smoke tests and QoS checks toward live DDS/RMW discovery, latency, reliability and network fault scenarios.

ROADMAP

Simulation-to-deployment

Plan simulator regression, hardware-in-the-loop evidence, robotics workload packaging, Kubernetes/edge orchestration and runtime telemetry. These are not analyzer v1.1.0 capabilities.

Strategy: build above ROS 2, contribute useful work upstream, and research independent robotics architecture only if measured limitations justify it. DAEMON ACE is not a ROS 3 distribution and does not claim to replace ROS 2.
07 / LIVE COMMUNICATION ASSURANCE

MOVE FROM QOS CONFIGURATION REVIEW TO LIVE ENDPOINT TESTS.

DAEMON ACE now includes a separate ROS 2 communication probe. It creates publisher/subscriber endpoints, tests selected reliability and durability request/offered combinations, checks transient-local late-joiner retention and records incompatible-QoS events.

LIVE PROBE TOOL · v1.0.0

Six DDS QoS scenarios

Positive message-flow tests, expected incompatibility tests and transient-local retained-sample verification.

RMW MATRIX

Fast DDS + Cyclone DDS

CI matrix targets Humble, Jazzy, Lyrical and Rolling with two named RMW implementations. Only completed green jobs count as validated combinations.

VERSIONED EVIDENCE

Communication report

Capture environment, expected/observed result, messages, incompatible-QoS events and local timing observations in schema-v1 JSON.

LIVE COMMUNICATION PROBE
source /opt/ros/$ROS_DISTRO/setup.bash

07 / VALIDATION BOUNDARY

BUILD PASS IS NOT ROBOT QUALIFICATION.

Static API rules are heuristic and may produce false positives or miss indirect usage. The separate Communication Assurance v1.0.0 probe tests six selected live endpoint scenarios, but it is not exhaustive DDS/RMW interoperability qualification. A successful colcon build does not prove application correctness, runtime behavior under load, simulator fidelity, physical hardware readiness, real-time performance or safety certification. Those require separately scoped tests, environments and authorization.
