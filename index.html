THE SIGNATURE DIFFERENTIATOR

DAEMON Proof-Loop™

Proof before production. ACE should not ask you to trust an AI-generated change blindly. It should show what it proposed, what was tested, what passed, what remains uncertain and what it expects to change.

POWERED BY PRE-FLIGHT TWIN™

Test the change in a twin. Not on your customers.

Before an authorized production change, the intended design is evaluated in an isolated test environment that approximates the relevant infrastructure state. The twin's fidelity, data freshness and test coverage are disclosed—because a simulation is useful only when its limits are understood.

01 / MIRROR —Capture approved configuration, dependencies and relevant runtime signals.
02 / CHALLENGE —Run defined load, failure, policy and security test scenarios in isolation.
03 / COMPARE —Compare baseline and proposed behavior, capacity and modeled cost.
04 / EXPLAIN —Show evidence, test coverage, assumptions and unresolved risks.
05 / APPROVE —Require an authorized human decision before production execution.
06 / VERIFY —Observe the rollout, check agreed health signals and preserve an audit trail.
THE RECEIPT OF SAFETY

Give decision-makers proof they can understand.

Replace opaque AI output with a concise change record: what ACE intends to do, the evidence behind the recommendation, the risks it found, the estimated impact and the exact approval being requested. The Receipt of Safety is designed to support internal security reviews, change-control decisions and audit preparation with traceable findings, assumptions, scope and human-review history—not to certify compliance or guarantee an audit outcome.

DAEMON ACE · THREE CHECKPOINT ARCHITECTURE
Three gateways. One evidence-led path to production.
DAEMON ACE is being designed to evaluate infrastructure changes at the code, cluster and live-network layers. Each checkpoint has a distinct enforcement boundary, a verifiable evidence record and a human-controlled exception path.
CHECKPOINT 01 · CODE GATEWAY
GitHub / GitLab Pull Request Guard
Planned repository integration: a GitHub App or GitLab webhook receives authorized pull-request events, evaluates changed infrastructure files and returns policy results to the review workflow.
  • Detect risky patterns such as public SSH ingress, wildcard IAM permissions and privileged/root containers.
  • Run deterministic policy checks and supported validation before reporting a result.
  • Publish a Receipt of Safety with findings, proposed remediation and evidence references.
  • Repository branch protection can require a passing status check before merge.
PLANNED · NOT CONNECTED
CHECKPOINT 02 · CLUSTER GATEWAY
Kubernetes Admission Control
Planned validating admission integration: Kubernetes asks a customer-deployed, highly available admission service to evaluate a workload before the API server accepts it.
  • Verify signed, unexpired approval evidence bound to the exact workload configuration and relevant policy version.
  • Reject non-compliant or unapproved requests according to customer-defined fail-open/fail-closed policy.
  • Record admission decisions and evidence identifiers for audit review.
  • Keep human approval and emergency break-glass procedures under customer control.
PLANNED · NOT DEPLOYED
CHECKPOINT 03 · LIVE-SYNC SENTINEL
Drift & Network Exposure Detection
Planned scheduled, read-only cloud inventory and drift detection for customer-authorized AWS/Azure resources, identity policies, security groups and ingress routes.
  • Compare observed state with approved configuration and policy baselines.
  • Flag unexpected public exposure, IAM changes and configuration drift.
  • Generate a proposed rollback/remediation diff for review—not an automatic production change.
  • Route alerts to configured Slack/Teams destinations after authenticated integration.
PLANNED · NOT RUNNING
HOW THE CHECKPOINTS WORK TOGETHER
Evidence follows the change.
A Receipt of Safety must be more than a green badge. It should be cryptographically bound to the exact artifact, policy version, test results, approval identity and validity window. Any material configuration change invalidates the prior approval.
01 · PROPOSECode change or infrastructure request enters the workflow.
02 · VALIDATEPolicy, schema and environment-appropriate tests run within declared limits.
03 · AUTHORIZERequired human approval is recorded against the exact change.
04 · ENFORCERepository checks and admission controls evaluate the approved evidence.
05 · OBSERVERead-only inventory detects drift from the approved state.
06 · RESPONDACE proposes remediation; authorized operators decide and execute.
Important engineering boundary: GitHub branch protection can block merges only when the repository owner enables required status checks. Kubernetes admission enforcement requires installation, availability, certificate management and correctly scoped policies. Neither mechanism can guarantee that zero unsafe changes ever reach production. A scheduled 15-minute scan is a proposed cadence, not real-time detection; detection latency depends on scan interval, API limits and integration health. Automated rollback is not enabled or promised.
