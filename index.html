REFERENCE IMPLEMENTATION PATH · OPEN-SOURCE PRIMITIVES

  

   
Telemetry & signals
OpenTelemetry Collector + Prometheus for metrics and traces; eBPF tooling such as Cilium or Tetragon for selected kernel, network and process signals. GPU-specific health still needs vendor/device exporters and validated mappings. Adaptive sampling requires configured collector or backend policies—not an automatic OTel switch by itself.

   
Policy-as-code
OPA/Rego + Conftest for policy proposals and CI fixture testing. A receipt-backed regression suite would need a defined, authorized D1 query/export contract, normalized historical inputs and reproducible replay; synthetic fixtures alone cannot prove zero false positives.

   
Identity & containment
Cilium NetworkPolicy for Kubernetes networking; SPIFFE/SPIRE for workload identity; edge-specific nftables and ROS 2 lifecycle integrations where appropriate. Identity expiry, policy denial or a lifecycle transition is not a substitute for independent robot safety systems or a validated emergency stop.

   
Chaos & simulation
Chaos Mesh for authorized Kubernetes staging experiments; Gazebo or NVIDIA Isaac Sim for ROS 2 simulation and sim-to-real test design. CI must isolate targets, define abort conditions and store test evidence. The current Pre-Flight Twin™ is a scenario-planning prototype, not an active fault injector.

  

  
These are candidate integration choices, not installed dependencies or connected services. D1 and SHA-256 receipt records provide an evidence foundation; they do not by themselves provide OPA history replay, fleet identity, signing, runtime enforcement or tamper-proof external attestation.

HOW THE CHECKPOINTS WORK TOGETHER
TRACE EVERY CHANGE TO ITS RELEASE EVIDENCE.
A Receipt of Safety must be more than a green badge. It should be cryptographically bound to the exact artifact, policy version, test results, approval identity and validity window. Any material configuration change invalidates the prior approval.
01 · PROPOSECode change or infrastructure request enters the workflow.
02 · VALIDATEPolicy, schema and environment-appropriate tests run within declared limits.
03 · AUTHORIZERequired human approval is recorded against the exact change.
04 · ENFORCERepository checks and admission controls evaluate the approved evidence.
05 · OBSERVERead-only inventory detects drift from the approved state.
06 · RESPONDACE proposes remediation; authorized operators decide and execute.
Important engineering boundary: GitHub branch protection can block merges only when the repository owner enables required status checks. Kubernetes admission enforcement requires installation, availability, certificate management and correctly scoped policies. Neither mechanism can guarantee that zero unsafe changes ever reach production. A scheduled 15-minute scan is a proposed cadence, not real-time detection; detection latency depends on scan interval, API limits and integration health. Automated rollback is not enabled or promised.
